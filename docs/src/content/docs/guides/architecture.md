The right mental model is not "one universal calendar API." It is **one stable SDK core with provider capabilities exposed explicitly**.

## The three layers

```
your app
   │
   ▼
CalendarSdk  ──►  services: accounts · calendars · events · availability · subscriptions · sync
   │                    │
   │                    ├──►  StorageAdapter   (accounts, tokens, calendars, events, cursors, subscriptions)
   │                    └──►  getToken()       (cache → storage → refresh via provider)
   ▼
ProviderAdapter (one per provider)
   │
   ▼
Transport (fetch + retry/backoff)  ──►  Google / Microsoft Graph / CalDAV
```

1. **Services** implement provider-agnostic workflows: capability checks, token resolution, storage persistence, logging.
2. **Provider adapters** implement the `ProviderAdapter` interface — pure API translation between the canonical model and each vendor's wire format. The core never imports a vendor SDK.
3. **Storage** is a set of narrow repository interfaces behind `StorageAdapter`. Every service reads and writes through it, which is what makes the SDK stateful and queryable offline.

## IDs: SDK ids vs provider ids

Every stored resource has two identifiers:

- `id` — a stable UUID generated by the SDK. This is what you pass to service methods (`sdk.events.update(eventId, …)`).
- `providerId` — the vendor's identifier, used internally when calling provider APIs.

This means the SDK's ids survive provider quirks (Google event ids, Graph ids, CalDAV hrefs) and stay stable across moves and re-syncs. Raw provider payloads are preserved on `raw`, and provider-specific extras live in `extensions`.

## Storage-backed reads

Services persist what they fetch:

- `calendars.list(accountId)` fetches from the provider **and saves** each calendar.
- `events.list(calendarId, query)` fetches from the provider **and saves** each event.
- `events.get(eventId)` / `calendars.get(calendarId)` read **from storage only** — they never hit the network.

Consequently, always call `calendars.list` for an account before operating on its calendars or events; other services resolve the calendar (and its `accountId` and `providerId`) from storage.

## Token lifecycle

The SDK factory builds a `getToken(accountId)` closure shared by all services:

1. Check the in-memory token cache (respecting `expiresAt`).
2. Fall back to `storage.tokens.get(accountId)`.
3. If expired and a refresh token exists, call the provider's `auth.refreshToken`, persist the new token set, and update the cache.
4. If refresh fails, mark the account `expired` and return `null` — the calling service then throws `AUTH_REQUIRED`.

You never handle refresh manually in application code. See [Authentication](/guides/authentication/).

## Capability checks

Each account stores a `CapabilityMap` snapshot taken from its provider at connect time. Services check it before calling the provider — e.g. `events.create` throws `CAPABILITY_UNSUPPORTED` on a provider without event creation rather than letting the vendor API fail obscurely. See [Capabilities](/guides/capabilities/).

## Cross-cutting concerns

- **[Hooks](/guides/hooks/)** — a typed event emitter (`request`, `sync`, `subscription`, `auth`, `error`, `rate_limit`) for observability.
- **[Errors](/guides/error-handling/)** — every failure is a `CalendarSdkError` with a stable `code`, `retryable` flag, and human `remediation` hint.
- **[Transport](/reference/transport/)** — a shared `fetch` wrapper with exponential backoff, jitter, `Retry-After` support, and sensitive-header redaction.
